# Flutter Harness
Use native SDK/components and the deterministic CLI, not invented command sequences.
CLI prefix: python3 .flutter-harness/bin/harness.py
No Skills or MCP by default; do not call disabled skills or delegate routine runtime commands to General. Read only the relevant project sources. For architecture/theme read .flutter-harness/PRODUCT.md; for material behavior, UI, or complex work read the respective BEHAVIOR.md, DESIGN.md, ORCHESTRATION.md in .flutter-harness/templates/product.
For a new task use CLI begin <feature-branch> (clean checkout) before runtime work; it validates the installed managed revision against the fetched base. If different, stop for owner sync/restart. Status reports actual state. Implement only the requested behavior; preserve data and unrelated work. Use scaffold <name> <needed layers> when useful. Standard Material 3, feature-first MVVM, adaptive system theme.
Write focused executable acceptance tests for material behavior, including rejected writes and reload for persistence; no arbitrary test quotas. Inspect the diff once. Run the exact CLI check command once on the final candidate; it resolves dependencies, formats and verifies. Fix failures rather than weakening tests. Do not rerun unchanged checks.
For material UX read DESIGN.md before edits. Run CLI launch auto before material UI edits; it chooses/pins the first working iOS → Android → Web target. Inspect the baseline with representative data. Do not probe/build other platforms without actual platform-specific risk. Plan current screen/interaction evidence in work/visual-plan.json. Use standard Material 3 patterns, visible selected states and clear mode names by default even when omitted from the task. Use CLI launch/capture and visual-evidence before reviewer dispatch; compare actual populated light/dark captures with baseline. For meaningful layout changes test compact/medium/expanded widths and live resize/state preservation with widget tests, not three builds. Keep small user-requested changes focused; no full redesign or unrelated visual iterations. Use CLI e2e only for meaningful platform/critical risk or explicit request; known initial state, scripted assertions. No all-platform E2E ritual.
Default Luna Medium, one parent. Independent reviewer for interacting behavior, risky or large changes and material UI; follow the guard's actual effort and verdict. Optional advisor and workers only per ORCHESTRATION.md. No automatic premium escalation.
For delivery write ignored .flutter-harness/work/delivery.json with message, title, body, exact files (all task dirty paths), review_required and required_e2e. For material visual/interaction changes (including focused changes) set visual_required and visual_interaction (true if changed interaction needs capture) in the manifest. Prepare the manifest and semantic risk flags before the final check/review; the script appends actual verification outcomes. Invoke exactly: python3 .flutter-harness/bin/harness.py deliver
Immediately after acceptance passes, invoke deliver before any final response. It checks evidence, stages, commits, pushes with owner approval, reconciles one PR and writes the current receipt. If interrupted, retry only deliver with approval, not checks or separate Git/PR commands. Never publish via other commands; never auto-merge. If required evidence is missing/denied, stop with BLOCKED/INCOMPLETE. Only report DONE after deliver returns PASS with its current receipt; a PR alone is not completion. Only report actual checks.
