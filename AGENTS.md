# Flutter Harness
Use native SDK/components and the deterministic CLI, not invented command sequences.
CLI prefix: python3 .flutter-harness/bin/harness.py
No Skills or MCP by default; do not call disabled skills or delegate routine runtime commands to General. Read only the relevant project sources. For architecture/theme read .flutter-harness/PRODUCT.md; for material behavior, UI, or complex work read the respective BEHAVIOR.md, DESIGN.md, ORCHESTRATION.md in .flutter-harness/templates/product.
If CLI status reports workspace, use its assigned branch and runtime; never switch to another branch/worktree. Owner creates/starts/cleans workspaces using workspace.py. For a new task use CLI begin <feature-branch> once (clean checkout) before runtime work; it validates the installed managed revision against the fetched base. If different, stop for owner sync/restart. Status reports actual state. Implement only the requested behavior; preserve data and unrelated work. Use scaffold <name> <needed layers> when useful. Standard Material 3, feature-first MVVM, adaptive system theme.
Write focused executable acceptance tests for new interaction state transitions (open/close, preserve/clear, cancel/save, failed writes as applicable), not only updated locators. Write tests for material behavior, including rejected writes and reload for persistence; no arbitrary test quotas. Inspect the diff once. Run the exact CLI check command once on the final candidate; it resolves dependencies, formats and verifies. Fix failures rather than weakening tests. Do not rerun unchanged checks.
For material UX read DESIGN.md before edits. Run CLI launch auto before material UI edits; it chooses/pins the first working iOS → Android → Web target. It automatically captures the initial light baseline before edits. Inspect it with representative data; if incomparable or unavailable, state why, never substitute another task image. Do not probe/build other platforms without actual platform-specific risk. Plan current screen/interaction evidence in work/visual-plan.json. Use standard Material 3 patterns, visible selected states and clear mode names by default even when omitted from the task. After edits prepare delivery and run canonical check before launch auto; changed candidates without current checks cannot launch automatically. Reuse baseline receipt. Prepare any scripted scenarios before check. Use capture-plan for multiple scripted states in both themes (reuses valid identical script/image receipts; --refresh LABEL recaptures a changed state), or capture for inspected states, then visual-evidence before reviewer dispatch; compare actual populated light/dark captures with baseline. For meaningful layout changes test compact/medium/expanded widths and live resize/state preservation with widget tests, not three builds. Keep small user-requested changes focused; no full redesign or unrelated visual iterations. Use CLI e2e only for meaningful platform/critical risk or explicit request; known initial state, scripted assertions. No all-platform E2E ritual.
Default Luna Medium, one parent. Focused independent review uses Medium; substantial/risky/large changes use High. Independent reviewer for interacting behavior, risky or large changes and material UI; follow the guard's actual effort and verdict. One bounded independent adjudication is available for a disputed finding on unchanged evidence, never repeated asks for PASS. Optional advisor and workers only per ORCHESTRATION.md. No automatic premium escalation.
For delivery use CLI prepare-delivery --message "commit" --title "PR title" --body "summary" [--review] [--visual] [--interaction] [--e2e ios] before final check/review. Inspect exact dirty scope first; the CLI writes all task dirty paths and valid typed flags, default required_e2e []. Use --interaction for changed visual interactions (implies --visual); --review for other semantic risks. Only explicitly require E2E for actual platform/critical risk. Refresh the manifest if file scope changes; never relax required evidence. the script appends actual verification outcomes. Invoke exactly: python3 .flutter-harness/bin/harness.py deliver
Immediately after acceptance passes, invoke deliver before any final response. It checks evidence, stages, commits, pushes with owner approval, reconciles one PR and writes the current receipt. If interrupted, retry only deliver with approval, not checks or separate Git/PR commands. Never publish via other commands; never auto-merge. If required evidence is missing/denied, stop with BLOCKED/INCOMPLETE. Only report DONE after deliver returns PASS with its current receipt; a PR alone is not completion. Only report actual checks.
