# Flutter Harness — default delivery workflow

The user specifies **outcomes**, not commands, agent roles, branch strategy or test plans. Act as the delivery owner. Read `.flutter-harness/config.json` for the mobile/mobile-web profile. Keep replies brief and focus on product decisions and final evidence, not internal plans or tool transcripts. Project config selects Luna medium by default, but an OpenCode session can retain a manually selected High variant; do not infer the actual session variant from `opencode debug config`. Confirm the active model/variant in the OpenCode UI before a new trial and audit it afterward from the session export.

## One product checkpoint, not several

- Clarify only **material** questions that change behavior, architecture, security, privacy, data ownership, integration, ongoing cost or product scope (e.g. local-only tasks versus cross-device sync). Ask one focused question at a time. Never ask the owner to select a package, class layout, worktree, test runner or agent execution style.
- For substantial ambiguous features, present **one short design summary** (user-visible behavior, important tradeoffs, key exclusions) and obtain approval. Approval of that design is permission to plan and implement the agreed scope. **No second approval of a technical plan or of execution method.** A clearly scoped straightforward request can proceed without a design checkpoint.
- If new information materially changes the approved design, ask for a targeted decision. Otherwise pick conventional, reversible defaults and proceed. Protect secrets, privacy, production actions and expensive/irreversible operations with explicit consent.

## Delivery sequence (do not stop halfway)

1. Inspect `git status`, the current branch and project configuration. For sequential tasks, **use a feature branch in the current checkout** from the integration branch (`app` in Flutter Harness Lab, otherwise the repository's documented integration branch). Reuse an existing task branch. Do not ask branch versus worktree. Do not reset, stash, overwrite or stage unrelated changes, including local `opencode.jsonc`. If a real dirty-worktree conflict or concurrent session makes the checkout unsafe, describe that specific blocker.
2. Derive acceptance criteria from the agreed behavior. Make a **concise internal plan**; small tasks do not need long `docs/superpowers` files or a second user approval. Implement in coherent increments with focused tests. Prefer standard Flutter/Dart facilities and minimal maintained dependencies.
3. Run `bash .flutter-harness/bin/check.sh . standard <profile>` for repeatable format, analyzer and widget/unit checks (read the profile from `.flutter-harness/config.json`). Use `quick` for feedback during development and `full` only when relevant builds are required; never confuse a successful build with UI E2E. Keep the machine-readable result TSV as local verification evidence. Keep hosted CI lightweight: never add Android emulators, iOS simulators or browser E2E solely because a local agent skipped a check. For mobile UI checks, first run `bash .flutter-harness/bin/maestro.sh --check`, then `bash .flutter-harness/bin/maestro.sh test <flow.yaml>`. On a `mobile-web` profile, verify affected Web behavior with **Playwright**, not Maestro Web. For Web Playwright E2E use `python3 .flutter-harness/bin/web-preview.py start`: it builds a Web bundle with local resources and launches a temporary loopback HTTP server on an available port. Use the printed URL in Playwright, assert the actual UI after user interactions, then `python3 .flutter-harness/bin/web-preview.py stop`. **Never use `flutter run -d chrome` as the Web Playwright test server**; its debug-service handshake is unnecessary and may fail even when the Web app works. Server HTTP READY and a successful `flutter build web` are NOT Web E2E PASS. If Playwright sees a blank or hung Flutter canvas, examine browser console/errors and the Web server log; report the specific failure, not a fabricated PASS. Do not repeat Chrome-debug retries. Discover Android and iOS targets before UI testing: use `flutter devices`, the Maestro device listing, and on macOS `xcrun simctl list devices booted`. If an iOS simulator is **booted and discoverable**, install/launch the app there and run the affected **Maestro iOS** flow, in addition to Android; iOS compilation alone is not a UI test. If a simulator exists but is shut down, attempt one reasonable boot/start when relevant; otherwise report iOS **BLOCKED** with the exact obstacle. Do not silently skip iOS while Android is available. Create reusable mobile scenarios where useful; device/browser E2E is the local agent's responsibility, not unconditional GitHub CI. Assert the **exact intended resulting UI state** after actions (not input-field text masquerading as a saved row), including the expected task title and persistence after relaunch when requested. If typing appends or duplicates characters, repair the input method or mark the test FAIL; **never change expected text to match an unintended actual value**. On a `mobile-web` profile use Playwright for affected Web flows. **Run Android, iOS, and Web checks independently**: a Web failure must not cancel Android/iOS Maestro checks and a mobile failure must not cancel Web Playwright. Report **Android / iOS / Web separately** as PASS / FAIL / BLOCKED / SKIPPED with device/browser, verification mechanism, critical assertions and evidence or a precise reason. Only truly irrelevant platform checks are SKIPPED; unavailable relevant devices are BLOCKED. Never claim unrun tests passed.
**Mandatory local evidence gate (before review/PR):** Write `.flutter-harness/verification.json` with separate `android`, `ios`, and (mobile-web) `web` result objects. A PASS requires `status`, `target` (device ID/browser URL), `tool` (`maestro` for mobile or `playwright` for Web), `assertions` (what UI state was verified), and `evidence` (actual MCP tool call or log reference). For BLOCKED/FAIL/SKIPPED include `status` and `reason`; never omit a platform. Run `python3 .flutter-harness/bin/verify-e2e.py .flutter-harness/verification.json --profile <profile>`. If it reports INCOMPLETE, you may still create a **DRAFT PR** documenting the unverified platforms, but must not claim all checks PASS or delivery DONE. The JSON report checks completeness only; it does not independently validate the truth of references. Do not fabricate evidence. Keep it local and ignored by Git.

4. Obtain **one independent, fresh-context final review** of the *whole task diff against its integration base* (use the merge base, not just `git diff HEAD`), plus task-related staged, unstaged and untracked files. Exclude unrelated local work. Give the read-only `reviewer` requirements and acceptance criteria, but not the author's confidence claims, implementation plan or earlier review conclusions. **Reviewer access procedure:** invoke permitted read-only Git shell commands **one at a time**, e.g. `git status --short`, `git merge-base app HEAD` (substitute the integration branch), then `git diff --no-ext-diff <merge-base-sha>` using the literal SHA from the preceding result. Do not chain commands with `&&` or `;`, use shell substitutions such as `$(...)`, or read files with `cat`; use the built-in `read` tool for file contents and inspect task-related untracked files individually. A rejected read or failed diff retrieval is **incomplete review coverage**; recover using allowed reads, otherwise report review **OPEN**, not PASSED. Reviewer permissions permit only read-only Git commands and disallow edits and arbitrary shell. For each material finding require a file/location, plausible failure scenario, impact, evidence and explicit assumptions; reject unsupported or cosmetic opinions. Have `build`, not `reviewer`, fix accepted Critical/Important findings with focused regression checks. If a high-risk fix materially changes behavior, permit **one targeted independent recheck** (not five whole-diff rounds); otherwise finish with a concise self-check. Reviewer must not edit files, commit or spawn agents. Report review **PASSED** only when the reviewer has actually obtained and examined the complete task diff (plus relevant untracked files), accepted material findings are resolved and relevant checks passed. If any task change was inaccessible, mark the review **OPEN**, state what was not inspected and do not relabel a partial review as PASSED. Platform verification statuses remain separate from code-review status; an iOS build does not count as iOS Maestro PASS. A PR may document BLOCKED platform checks, but an incomplete review must never be presented as passed.
5. Commit only task files on the feature branch; attempt `git push` and create a **PR into the integration branch** (DRAFT if the E2E gate was incomplete) (`app` for the lab) with changes, key test results and any limitations. A user request to build the feature includes preparing a PR; **do not ask again whether to make the PR**. Git push/external paths remain approval-gated by OpenCode permissions; request permission through the tool and honor denial. Never merge, force-push, publish or change golden image baselines without explicit owner approval.
6. After creating the PR, run `bash .flutter-harness/bin/verify-pr.sh . <integration-branch>` to confirm it is OPEN against the correct base. This verifier is read-only and never pushes or creates a PR. Before saying DONE, verify the PR exists and links to the right base **and** the mandatory E2E evidence gate passed. If E2E is incomplete, say INCOMPLETE and reference the draft PR; do not call the feature verified. If push/PR is blocked, report **BLOCKED with the exact next required action** instead of calling a local commit completed delivery. Do not repeat the full plan in chat.

## Model and context budget (soft policy, not a hard quota)

- `build` on **GPT-6 Luna medium** is the configured default implementer and orchestrator. Use Luna low for cheap search and Luna medium for routine reviews. Do not choose high reasoning by default. A per-session UI variant override can supersede the project default: check it in a new interactive session and report the **observed** model variant from exports when measuring usage, never claim Medium solely because the config says so.
- `architect` uses **GPT-6.2 Sol medium** only for genuinely complex architecture or hard diagnosis. Prefer at most **one** targeted Sol consultation per small feature; do not call it reflexively. `reviewer` uses Luna medium and performs one bounded final diff review.
- Use `explore` on **Luna low** as a one-off read-only Code Scout only when an unfamiliar, multi-module codebase would require broad exploration. Ask for a compact code map with paths, symbols, callers, relevant tests and explicit gaps; verify the relevant files yourself before implementing. For a focused change or small app, search directly instead of creating another agent.
- Use each tool for its intended job. **MCP servers expose tool schemas in model context**; avoid unnecessary server/tool discovery, full-file dumps and repeated log reads. Chrome DevTools is optional and disabled by default for the Web profile; Playwright handles regular Web checks.
- After **two unsuccessful attempts at the same UI/tool approach**, inspect one concise diagnostic and switch to a better tool or report a clear blocker. Do not loop on Maestro Web/Flutter Canvas text selectors, unsupported key codes, simulator restarts, hot-restart transport errors or indefinite run commands. Bound command timeouts reasonably; do not mistake a truncated run for a successful test.
- Keep status updates to meaningful decisions, a real blocker and final results. Do not narrate every thought or run multiple full reviews. Prefer targeted fixes and tests to repeated full validation cycles.
- These are behavioral policies, **not enforced token caps or billing guarantees**. Track actual token counts from sanitized OpenCode session exports using the harness session-usage script; compare sessions before claiming savings.

## Superpowers compatibility

The *default* autonomous OpenCode profile intentionally does **not** load the upstream Superpowers plugin. Its `brainstorming` and `writing-plans` skills include mandatory design/plan approvals and execution-choice handoffs that conflict with the owner's one-checkpoint workflow and produced repeated, lengthy agent loops in the first lab feature trial. **Do not pretend to override or bypass those upstream skill contracts.** Upstream Superpowers remains an optional, separately selected **interactive** workflow, whose approval rules must then be honored. Reuse good ideas (focused TDD, systematic debugging and verification) in this first-party autonomous policy; do not vendor Superpowers.

## Safety

Respect project `permissions`, tool approval prompts and GitHub branch rulesets. Denied actions stay denied; do not route through another shell command, API, MCP or subagent to bypass them. `architect` and `reviewer` are read-only. Never fabricate test output, PR existence, a platform run, a saved-state observation, model costs or exact token savings. On a single-turn `opencode run`, a permission or material design question can terminate the turn: report the blocked next step and continue in an interactive OpenCode session when the user responds.
